## Known limits (S1)

- Prose is refused structurally (actions/observables are dotted tokens, input/value strings are short space-free tokens), but a single-word token can still be a name. A human reviews every scenario PR for public-data hygiene.
- matrixRow is required for money, permission and tenancy records but only format-checked: the SCRUM-486 matrix is not machine-readable yet, so membership cannot be joined until it is (S2/S3).
- A parameterized (test.each / describe.each) named check is refused: one record per case, or a runner census in S3.
- Skip detection is static and best-effort (indirection such as options held in a variable can beat it); the S3 runner census (named test executed and passed, not skipped or expected-fail) is the binding proof.
- An active cloud-level record is refused until a cloud runner exists (SCRUM-762); park it as a candidate.
- Free-text reasons (retiredReason/candidateReason, 300 chars) and impl.testName are only heuristically screened; reviewers check them for public-data hygiene.
- Records may not share one impl.file + testName; the title is not yet required to carry the scenario id (follow-up).
- impl.testName must equal the registered test title exactly (no substring binding).

## Record kinds

- `scenario` (default): actor + public-API steps.
- `rule` (owner ruling 2026-10-07): a pure-function money/permission rule (e.g. `saleEconomics`) described by `subject` + `inputs` instead of steps. Backend level, non-screen domain; still needs a ruling, a matrixRow and an exact `impl.testName`. Identity (de-dup) is subject + inputs + expected.
- SCRUM-595 loop-generated cases are one record per case, parked as `candidate` until the S3 runner census can bind generated titles (owner ruling 2026-10-07).

## Local record execution advisory (SCRUM-761 S3)

This entry requires Node 22.18.0 or later with native `import.meta.main` support; the pinned CI runtime is 22.21.1. Unsupported runtimes refuse instead of silently succeeding. Each declared option accepts one occurrence and one string value; repeated options refuse instead of choosing the first or last value. Supplied revision options must be nonblank full commit SHAs. Invalid CLI arguments exit nonzero without publishing a receipt because their output destination has not been validated.

The existing source directory and output parent are resolved physically before execution or publication. An external directory link pointing into source refuses; an output link to an external directory remains supported. The selected test file is passed to Vitest as an absolute positional path, so a literal filename beginning with `--` stays a test filter. These checks do not sandbox the caller-selected repository or protect against concurrent hostile directory replacement.

`node scripts/regression/runLocalExecution.mjs --scenario opening-all-families-public-rehearsal` resolves the existing record and actually runs its named top-level backend test with one Vitest worker, no watch, retry or file parallelism. This first supported opening path is a local `convex-test` harness observation. It neither certifies the rest of the library nor represents authenticated browser, platform, OCC or production evidence. The command runs on the checkout it is launched from: the host's working directory selects the source root, and an optional `--root <path>` only confirms that same directory (a different path refuses with `ROOT_CONTEXT_MISMATCH`). There is no output option: the receipt is always `result.json`, created exclusively inside a fresh evidence directory outside the source checkout, and the printed JSON reports its location. The default evidence directory is created fresh (owner-only) in the system temp directory after that location is checked to be outside the checkout; the receipt file is created exclusively (`wx`) and its handle is held for the whole run, so the final write goes through that descriptor and replacing the directory or a parent link while the child runs cannot redirect it; a pre-existing `result.json` refuses. The native report does not travel through any file: the Vitest reporter writes it to an extra pipe (fd 3) that only the Vitest main process holds, and nothing the child leaves on disk is read. Forked test workers do not inherit that pipe. A Vitest config executes in the main process and could write that pipe, so Vitest never runs from the working tree: the host exports the observed HEAD commit into a fresh directory outside the checkout and runs there. The blobs are written straight from the object database (`--no-replace-objects`, here and in the reporter's base-record reads) and each is re-hashed by Git itself (`git hash-object --no-filters`, never Node's SHA-1), so no smudge filter, attributes file, hook, replace ref or working-tree state can change the bytes; ignored, assume-unchanged, skip-worktree or hidden-untracked files cannot take part, and a tracked `node_modules`, a path that could leave or alias the export, or a symlink refuses. The bytes are the commit's own, with three stated differences: the executable bit is not restored, a Git LFS file stays its pointer text, and a submodule is an empty directory. The reporter and the Vitest main process are not read from the harness working tree either: its `scripts/`, `package.json` and `tsconfig*.json` are exported from the harness checkout's own HEAD the same way into a second directory, so an edit hidden with assume-unchanged or skip-worktree, an untracked or ignored shadow file, or any line-ending change in that working tree never takes part. The two files the CLI process itself runs from (`scripts/regression/runLocalExecution.mjs` and `scripts/trustedGit.mjs`) are loaded before any export exists, so they are compared with the harness HEAD's own bytes and a difference refuses with `HARNESS_NOT_COMMITTED` (verdict `UNAVAILABLE`, no test run). The only tolerated difference is an exact whole-file LF-to-CRLF conversion of a committed file that has no CR, which is what `core.autocrlf=true` produces; `\r\r\n`, mixed endings and any other byte are refused. The receipt records `harness: { head, closureMatchesHead }`. Stated limit: this is best-effort detection, not protection. An entry file that was itself tampered with can skip its own check, and an invoker who needs more must start the CLI from a trusted copy. The harness checkout must be a repository top level whose HEAD contains the reporter, else `HARNESS_UNVERIFIED`. Scope decision: Vitest reads no `.npmrc`, pnpm workspace file or lockfile when it runs, so those are install-time inputs and are not exported; `node_modules` of both checkouts is a trusted environment reached through links. Both directories are removed afterwards, the links first; if a link cannot be detached (the detach reports failure), everything else is still removed and the run fails with `EXPORT_CLEANUP_INCOMPLETE`; if a detach or removal throws, entries may remain, and the run fails with `EXPORT_CLEANUP_INCOMPLETE` too. Both hold on success and on every throw path. The receipt records `execution.from: "HEAD_EXPORT"`. Visible uncommitted edits still refuse with `SOURCE_NOT_COMMITTED`, so a verdict about HEAD is never read as one about an edited tree. The exported tree must have at most one config file (matched case-insensitively) and it must be a regular file, else `TRUSTED_CONFIG_REQUIRED`; a change to the exported files during the run is `SOURCE_CHANGED_DURING_EXECUTION`. Installed dependencies in `node_modules` are part of the trusted environment. `GIT_*`, `NODE_OPTIONS`, `NODE_PATH`, `VITE*`, `VITEST*`, `npm_config_*` and `PNPM_*` environment variables are not passed to Git or Vitest, and the fork pool is pinned on the command line. Stated limit: the committed config, the selected test and everything they import are the code under test and run with the invoker's privileges, so committed code can still forge a report; the receipt is local advisory evidence only, never a trusted attestation. A trusted embedding caller may pass an explicit `{ root, evidenceDirectory }` context to `main`; arguments never choose it. An optional `--base <full-commit-sha>` supplies the immutable base library for existing transition validation; default is the observed local HEAD. `--expect-head <full-sha>` checks a requested label against the locally observed Git HEAD, without making that observation trusted.

The native Vitest 4.1.9 Reporter reuses `loadLibrary`, `validateLibrary` and `validateTransitions`, and retains the selected record's fingerprint/status and any retirement reason. Only the two fields actually consumed by transition validation are projected from immutable base records; its runtime policy is unchanged. Native events supply the actual test ID, module/name/full name, literal project name (the unnamed default is empty), outcome, expected-failure option and retry/repeat/flaky diagnostics. Exactly one ordinary passing execution is required; zero, duplicate, skipped, unfinished, failed, expected-failure-as-pass, retries, incomplete reporting, unhandled errors and nonzero child exit refuse. Native IDs depend on project, module URL and test order; they are not a universal scenario ID. Built-in JSON status alone does not carry the expected-failure/identity evidence needed for this join.

The parent observes all Git-listed nonignored source files before and after execution and refuses changed source or unsupported source symlinks. HEAD/tree/digest/dirty state are **unattested local observations**; candidate code, environment variables, record actor labels and this output cannot manufacture trusted GitHub producer authority. In particular, no role is inferred from record steps or test metadata. FAIL and UNAVAILABLE exit nonzero locally. No workflow, required check, pin, registry or production switch is changed; these receipts are not a new release gate. CI artifact/run/controller binding and any required-check promotion remain separately scoped work.

`localExecution.test.ts` uses isolated temporary repositories and real child Vitest invocations to exercise runtime skip, dynamic expected failure, zero-case success, duplicate projects, changed source, missing binding, ruling drift, active demotion, retirement without reason and a mismatched requested HEAD. Runtime-indirect skip/fails fixtures deliberately exercise the definition validator's documented static-analysis limit; no validator is disabled. Fixture-only seed commits create real base objects, never commits on the application branch. The real opening record must also run separately against the final source; toy fixture results are not opening acceptance. See [Vitest reporters](https://vitest.dev/guide/advanced/reporters.html), with exact compatibility checked against the installed package rather than assuming newer documentation APIs.
