Status: PHASE 1 (design, dry run, tests). No deleting code exists or is authorised yet. Phase 2 runs only after the owner approves the exact dry-run manifest.

Owner rulings (2026-11-27): all DELETED deals and DELETED expenses are test or incorrect and are erased with their accounting events, journals and numbers as if never recorded; real, non-deleted data is kept byte-identical; the nine CANCELLED applications (deal numbers 6, 7, 10, 11, 12, 15, 16, 17, 21) and the three REVERSED treasury transfers are tests; deal-number gaps are accepted. Later the same day: deal 6's custody cash 468.500 JOD (journal JE-DPVS8JTXXP) and the same amount in finance-fee expense 6860 are a TEST entry whose resulting balance change is ACCEPTED and must be itemized per account; the 50.000 JOD deposit of 2026-11-14 is real and must survive.

## 1. Precedents and what is deliberately not copied

| Precedent | Causal mechanism (why it works) | Applies here? | Not copied |
|---|---|---|---|
| `convex/orgFinancialReset.ts` `resetOrgFinancialData` | Fail-closed: a table list, a survivor-reference preflight, batch deletes, a census test that fails when a table is added without a ruling | Yes: same list-plus-census discipline (`scripts/purgeImpactMapCensus.test.ts`) | It wipes a whole organization by table. This purge is by explicit ROOT, row by row. |
| `accounting/reversals.ts` | A reversal is an inverted journal; original + reversal net to zero and bump the same running snapshots, so removing both and subtracting both gross amounts restores the pre-posting state | Yes, provided every purged journal is half of a complete pair that nets to zero per account | Reversals append; the purge removes. The unwind rows the unwind produced are removed WITH the root, never alone. |
| `utils/openingVoidProof.ts` | A proof of zero net per account before anything is voided; refusal otherwise | Yes: the per-account net check | The opening void keeps the rows (status change). The purge deletes, so its proof is stricter and has an itemized, owner-approved exception list. |
| `treasuryTransfer.ts` | A transfer is an accountingEvent with no table of its own | The three transfer roots are events | n/a |

Causal invariant that makes the purge safe: a ledger balance is the sum of its journal lines, and each account's running snapshot is the sum of the gross debits and credits ever posted. If the removed lines net to zero per (account, currency, bank, period), every balance is unchanged; the snapshots only need their gross amounts reduced. Where the removed lines do NOT net to zero, the balance changes by exactly that net, which must be stated, itemized and approved before it happens.

## 2. Invariants

I1. Only named roots start the purge. A sale root must be deleted AND CANCELLED, an expense root deleted, an application root CANCELLED, a transfer root a REVERSED TREASURY_TRANSFER event; a live record is refused as a root.
I2. Every row removed is either a root, structural to a root, or ledger or derived from one. Everything else is byte-identical afterwards.
I3. A row that must survive and mentions a purged id (any field, array, payload, link, sourceId or idempotency key) makes the dry run REFUSE. It is never patched or orphaned silently. scripts/purgeImpactMapCensus.test.ts derives from the schema validator tree every `v.id()` that points into a purgeable table and fails unless its source table is scanned (66 tables by org index, the three root tables, journal lines through their parent journal, the organization row by id) or listed by name in PURGE_REFERENCE_COVERAGE; mutation controls prove the check can fail. The ONE exception is a kept row tied to the purge by a single clearable link field (R8): it is listed in `fieldClears` with its guarding state, not refused; a deposit's `resolutionSaleId` is listed only for an owner-approved exact deposit id and refuses (FIELD_CLEAR_NEEDS_APPROVAL) otherwise. The id-token scan finds ids as whole tokens only (see A4).
I4. Ledger events leave as complete pairs (original + reversal, both in the set), with their journals and lines.
I5. The removed lines net to zero per (period, account, currency, bank) EXCEPT what an owner-approved exception explains. An exception is {rootId, eventIds, journalIds, expectedNets[(periodId, accountId, currency, bankAccountId?, netMinor)]}: only the events and journals it names by exact id are exempt from pairing, its expectation is compared with the net of ITS OWN named journals per period (so two roots can neither share nor offset one), and whatever the expectations do not explain must still net to zero per key. A mismatch is EXCEPTION_MISMATCH, an unexplained net NONZERO_NET, a named id outside the purge set EXCEPTION_ROOT_NOT_IN_PURGE. A journal with no period is netted in a NONE bucket and refuses PERIOD_UNKNOWN.
I6. No removed journal is in a CLOSED or LOCKED period. A period without a record refuses.
I7. Each running snapshot reduced by the removal is at least as large as what is subtracted (no negative gross).
I8. The dry run writes nothing and every read is bounded. A table too large to read completely refuses; it is never silently truncated.
I10. A joinable row joins only if every reference it holds into a root-class table (sale, application, expense) is itself in the purge set; otherwise SHARED_WITH_LIVE and it does not join (claim chains through `restoredFromClaimId`, idempotency rows that mix live and purged ids). A purged row in a live money state (PURGE_LIVE_STATES: canonicalPayments VERIFIED/PENDING_SETTLEMENT/SETTLED, customerFinanceCompanyPayments CONFIRMED, paymentAllocations ACTIVE, receivableDocuments OPEN/PARTIALLY_PAID/PAID/WRITTEN_OFF, depositApplications APPLIED/REVERSING, depositCancellationPendings PENDING/QUARANTINED/FORFEITED, financeDealCustody OPEN, vehicleCommitmentClaims ACTIVE, vehicleSupplierPayables PENDING/NOT_YET_DUE/DUE_ON_SALE/PARTIALLY_PAID/PAID/DISPUTED, dealUnwinds ACTIVE, commandIdempotency STARTED) refuses LIVE_STATE_ROW unless its exact id is in `approvedLiveRowIds`; an approved id that is not in the set refuses APPROVED_ROW_NOT_IN_PURGE. The census requires every purgeable table with a status lifecycle to be a live state or justified in PURGE_NOT_LIVE_STATUS.
I11. Ledger pairs are complete in BOTH directions for events and journals: the original names its reverser and the reverser names the original, both purged, journals POSTED or REVERSED; a reversal that was itself reversed needs its reverser in the set.
I9. The erase (Phase 2) acts only on a manifest this query returned `ok: true` for, and erases an audit row only when its SUBJECT is a purged id (I12, owner ruling A); an audit row about a kept record that mentions a purged id refuses AUDIT_MIXED_SUBJECT.

## 4. Attack list (what an adversary or a mistake would do)

A1 Purge a live record by passing its id as a root: refused by I1 (`ROOT_NOT_ELIGIBLE`).
A2 Hide an unreversed money movement inside a test deal (deal 6): refused unless the owner names the exact accounts and amounts; a typo in the amount refuses (`EXCEPTION_MISMATCH`).
A3 An exception that covers one of two moved accounts: the other stays non-zero and refuses (`NONZERO_NET`).
A4 A surviving row that mentions a purged id only in free text or an idempotency key: caught by the id-token scan across every scanned table (`SURVIVING_REFERENCE`). Not caught: an id glued into a longer token with no separator.
A5 A purged journal in a closed period, whose snapshot cannot be re-derived: refused (`CLOSED_PERIOD`).
A6 Snapshot shards that cannot absorb the reduction: refused (`SNAPSHOT_UNDERFLOW`).
A7 A table that grows past the read cap between the dry run and the erase: refused (`OVER_BOUND`) rather than half-read; Phase 2 must re-run the manifest and compare hashes in one transaction.
A8 A reversal half left behind: refused (`INCOMPLETE_REVERSAL_PAIR`, `JOURNAL_NOT_PAIRED`).

## 5. Five predicted ways the purge could still be wrong

F1 A real row mixed with a test id in one document (a payroll item listing a real and a purged sale; a commandIdempotency row). The scan only sees "mentions", so these appear as surviving references or are absorbed as derived rows; the owner must decide each mixed row (payrollItems, commitmentRoots).
F2 Shard attribution of the snapshots: the posting shard is not recorded, so the gross is subtracted from the total across shards, not the shard it was added to; any consumer that reads one shard (not the sum) would see a different number than before.
F3 (closed in round 1) An exception applied to the wrong root: it used to be summed across roots. Each exception is now compared with the net of its OWN named journals per period, so swapped or offsetting expectations refuse (EXCEPTION_MISMATCH).
F4 An audit row that explains a state the purge erased. Phase 1 position (superseded): audit rows were kept by default and then referenced ids that no longer exist. Current (owner ruling A, phase 1b, I12): a row whose subject is purged is erased with it, and a row about a kept record that mentions a purged id refuses AUDIT_MIXED_SUBJECT.
F5 (closed in round 1) A KEEP table holding a reference the scan does not read: the census now derives every reference into a purgeable table from the schema and fails unless its source table is scanned or named in PURGE_REFERENCE_COVERAGE (empty today: the eight references the first walk found in unscanned tables, the organization scan fields, journalLines, and the sales/application link fields, are all scanned now).

## 6. Two resolution options

Option A, selective purge (recommended): remove exactly the manifest above, with exceptions itemized. Could break: surviving references (commitmentRoots consumedBySaleId, payrollItems) which must be patched or kept first; (phase 1 only: audit logs would point at removed ids; since ruling A audit rows whose subject is purged leave with it) deal-number gaps (accepted).

Option B, tombstone/void instead of delete: keep every root and ledger row, mark them void (status), reverse deal 6's two events with real reversal journals, hide them from reports. Could break: nothing is erased, so the owner's "as if never recorded" is not met; reports filtering the voided states must stay correct forever; the deal numbers and notifications remain.

Accounting practice (not verified against a fresh source in this session): erasing posted ledger entries is normally replaced by reversing or correcting entries so the audit trail survives; a physical erase is acceptable only as an owner-ruled, one-time, documented correction of test data in a non-closed period. Option A is chosen because the owner ruled it, with one new purge audit row. The phase 1 position, "the audit trail kept in the audit logs", is SUPERSEDED by owner ruling A (phase 1b): audit rows whose subject is purged are erased with it. `finance-accounting-collections-audit.md` R2 (line 258: posted financial records must be immutable and corrections must be reversals) is OVERRIDDEN for this purge by owner rulings A and B/C for the listed test records only; it stays in force for every other record.

## 9. Documents consulted (fetched 2026-11-27) and what could not be checked

Fetched with WebFetch on 2026-11-27, and what each page supports here:

Supports the bounded design: the manifest's own budget is 24,000 documents (under 32,000) and a table over the 6,000 cap refuses. It also changes one claim: `db.get` calls count toward the 4,096 ranges, and the manifest reads each table once by index and reuses the rows (no `db.get` per event or journal), plus one query per journal and snapshot key; with the production set (about 170 events and 120 journals) that is far below 4,096, and the manifest now counts the ranges (`totals.rangesRead`, budget about 3,500, every db.get and db.query charged BEFORE it runs); Phase 2 must do the same. - https://docs.convex.dev/database/reading-data/indexes/ - an index range is a chain of `.eq` comparisons from the first index field; `.withIndex` bounds the documents read, `.filter` does not. Supports reading each table through an `orgId`-leading index (`q.eq("orgId", orgId)`) and never filtering by org; the census test proves all 66 index-scanned tables have such an index.
- https://docs.convex.dev/database/reading-data/ - `take(n)` returns the first n results, `collect()` returns all matches and assumes the result fits the transaction limits, a `take(10_000)` is used as a safeguard in the page's own example. ## 11. Phase 1b (owner rulings, second set, 2026-11-27): audit rows, payroll run roots, deposit roots, confirmed payment evidence

Rulings: (A) audit-log rows that mention purged records are deleted with them; (B) a CANCELLED payroll run that mixes purged and real sales is deleted; (C) kept REFUNDED deposits linked to purged sales are deleted if refunded; (D, revised by the coordinator the same day) finance application 21 is a purge root again: its CONFIRMED `customerFinanceCompanyPayments` row (2,800.000, evidence that the customer paid the lender directly, no posting) may leave ONLY when the owner approves that exact row id.

Precedent and the invariant reused (precedent protocol): the sale, expense, application and transfer roots of `purgeManifest.ts`. What makes them safe, and what is applied unchanged to the new roots: explicit root ids; an eligibility proof per root BEFORE it joins; closure only through the classified impact map; a kept row that mentions the set refuses (or is a listed one-field clear); per period/account/currency/bank netting to zero unless an owner-approved exception; one read budget (a read at its bound refuses OVER_BOUND); refuse on any doubt. New invariants
- I12 (audit rows). An audit row (`financialAuditLog.resourceId`, `adminAuditLog.targetId`) whose SUBJECT is a purged id is erased with it; the closure is never extended through an audit row. An audit row whose subject is NOT purged but whose text, payload or key mentions a purged id is never guessed at: AUDIT_MIXED_SUBJECT. Rows of the subject-purged kind that also name a kept row of a scanned table are listed in `auditRowsMentioningKept` (information for the owner, deleted per the ruling). Org-less admin audit rows (`orgId` absent) are read through the same index with `eq("orgId", undefined)`, under the same budget; a table too large refuses OVER_BOUND.
- I13 (payroll run root). Eligible only when: status CANCELLED; no payment fields on the run (paidAt, paidBy, paidMethod, paidBankAccountId); no accounting event naming the run or one of its items is POSTED and unreversed (PAYROLL_RUN_LEDGER_EFFECT), proved from events, not from the status; no payment evidence row names one of its items (employeeAdvanceRecoveries.payrollItemId, dealCommissionLines.payrollItemId, openingCommissionLiabilities.paidPayrollItemId: PAYROLL_RUN_PAYMENT_EVIDENCE). Its items (payrollItems.runId = the run) join as owned children and are exempt from the live-sale join guard (that is the ruling: a run mixing purged and real sales goes), because a draft item changes no sale, advance or line; any OTHER kept row that names the run or an item refuses (SURVIVING_REFERENCE).
- I14 (deposit root). Eligible only when: REFUNDED with refundedAmountMinor = releasedAmountMinor = amountMinor, nothing forfeited, hold not active, not an OPENING deposit (DEPOSIT_NOT_REFUNDED otherwise: HELD, FORFEITED, APPLIED, VOIDED, partly refunded); the deposit's POSTED unreversed events in the set are one or more DEPOSIT_RECEIVED events summing to the full amount and DEPOSIT_REFUNDED events summing to the full amount; EVERY counted receipt and refund must carry a journalEntryId whose journal is POSTED and is itself in the purge, otherwise DEPOSIT_REFUND_PROOF (a journal that is DRAFT or not POSTED gives DEPOSIT_REFUND_PROOF for the event plus JOURNAL_NOT_PAIRED for the journal; an event with no journal, or whose link was removed so the journal row is an unlinked orphan, gives DEPOSIT_REFUND_PROOF, plus JOURNAL_NOT_PAIRED for the orphan; amounts alone never prove a deposit, because journal-less events net to zero trivially). Round 3: the journal must also be BOUND to its event (journal.accountingEventId equals the event id; the posting engine sets it, postingEngine.ts line 693, but the schema field is optional, so an unbound journal fails closed), which also means no journal can back two counted events (a journal has one accountingEventId); and each counted event currency must equal the deposit currency. Journal line amounts are NOT compared with the event payload; the per-period/account/currency/bank net-zero proof is what constrains them; those events and journals are exempt from pairing only, the per-period/account/currency/bank netting still applies in full (so a refund in another period, or with another bank, refuses NONZERO_NET; in a CLOSED period, CLOSED_PERIOD); a deposit naming a kept sale/application/expense is SHARED_WITH_LIVE; a forward pointer into a purgeable row that is not in the set (canonicalPaymentId, singleVehicleCommitmentClaimId) refuses DEPOSIT_REFUND_PROOF. This supersedes `approvedFieldClearIds` for a deposit passed as a root; passing the same id in both refuses (APPROVED_ROW_NOT_IN_PURGE).
- I15 (confirmed evidence). A purged `customerFinanceCompanyPayments` row that is CONFIRMED refuses CONFIRMED_PAYMENT_EVIDENCE unless its exact id is in `approvedLiveRowIds`, and an approval never covers a row that has a ledger link (any accounting event, journal or canonical payment naming it, or named by it: CONFIRMED_PAYMENT_LEDGER_LINK). An approved id that is not in the purge set (another application or organization: such a row would name a kept application and be blocked by the join guard anyway) is the generic stale-approval refusal APPROVED_ROW_NOT_IN_PURGE. A purged application whose handoverStatus is HANDED_OVER (or has vehicleHandoverAt) refuses LIVE_STATE_ROW on financeApplications unless its exact id is approved, and the approval holds only while the I16 proof passes for EVERY vehicle the application names (vehicleId and each vehicleItems entry: all AVAILABLE, none naming the deal), no kept row names the application and no POSTED un-reversed event names it; an application that names no vehicle cannot be proven and refuses HANDOVER_LIVE_CONSEQUENCE.

## 12. Phase 1c (owner ruling 2026-11-27, Jira SCRUM-1023 comments 26166-26168): commitment roots and stale claims leave with their deals

Ruling: any amounts or holds hanging on cancelled deals are released; consumed commitment roots and stale claims leave with their deals. (The brief called this I16; I16 is already the stale-handover invariant of section 11, so this one is I17.)

Precedent and the invariant reused: the phase-1b proof modules (`purgeRootProofs.ts`, `purgeEvidence.ts`, `purgeHandover.ts`): a pure module over rows the manifest already read, a proof BEFORE a row leaves, a distinct refusal code per cause, fail closed, no approved id lifts a lineage fact. Not copied: the generic `approvedLiveRowIds` lift (a claim is judged by its rows, not by the owner's id) and the closure join guard (it blocks a claim that names a kept CANCELLED application, which is exactly the stale claim the ruling releases).

- I17 (commitment lineage). A `commitmentRoots` row joins the purge only when its status is CONSUMED, the sale that consumed it (`consumedBySaleId`) is itself in the purge, the root is bound to that sale row (same `vehicleId` and `customerId`: a sale has exactly one of each, `cashSales.schema.ts`) and it is the ONLY such root of that sale (`boundRoots`, before the closure). A root for another car or customer, or a second root of the same sale, does not join and, kept, refuses COMMITMENT_SHARED_LINEAGE (the schema writes `consumedBySaleId` once and has no back-link from the sale, so such roots cannot be told apart and none is proven). Its claims join with it unless a KEPT sale consumed one. An ACTIVE claim in the purge must be proven finished (a claim that is not ACTIVE holds nothing and is not judged on its evidence or holds): the sale that consumed it is purged, or its defining evidence row (`evidenceKind`: a deposit, a finance application or a reservation) is purged or terminal (REFUNDED deposit, CANCELLED application; a reservation has no terminal state) AND is bound to this claim (round 4: the evidence row belongs to the customer of the claim's root, names the claim's vehicle when it names any, and does not name ANOTHER kept claim as its own commitment through `deposits.singleVehicleCommitmentClaimId` or `financeApplications.currentCommitmentClaims`; otherwise it is not this claim's evidence and the claim refuses COMMITMENT_EVIDENCE_LIVE). Further, no ACTIVE `depositVehicleHolds` row points at it (by `sourceCommitmentClaimId`, or a legacy slice of the same deposit and vehicle). Refused, with their own code and never lifted by an approved id: COMMITMENT_ROOT_NOT_CONSUMED (a kept root that is not CONSUMED names the purge), COMMITMENT_EVIDENCE_LIVE (an ACTIVE claim rests on live kept evidence, on evidence that was not read, or on a row that is not bound to it), COMMITMENT_ACTIVE_HOLD, COMMITMENT_SHARED_LINEAGE (a kept deposit, application, hold, root or claim still points at a purged root or claim, a purged row names a kept root or claim, or the claim's root is kept and not current), COMMITMENT_CURRENT_FOR_VEHICLE (an ACTIVE claim whose kept root is OPEN is the car's live commitment). Every root and claim that leaves is itemized in `commitmentItems` with its evidence and the vehicle's kept OPEN root. Still read-only: no insert, patch, replace or delete, no scheduler, no public door.

Impact map rows (changed): `vehicleCommitmentClaims` keeps STRUCTURAL and its ACTIVE live-state rule, now tagged `code: "COMMITMENT_CLAIM"` so the generic LIVE_STATE_ROW skips it (judged in `purgeCommitments.ts`); `commitmentRoots` stays REFUSE_IF_REFERENCED (a kept root naming the purge still refuses, with a distinct code). `findSurvivors` takes the set of kept rows already judged, so one cause shows one code.
