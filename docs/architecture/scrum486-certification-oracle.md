## Queued consigned supplier VAT, SCRUM-782

The literal test `cron ticks with only valid period holds schedule no work or parked-range scans` measures the persisted scheduler records across three ticks with owned-VAT and zero-VAT holds; no job is added. This is harness evidence about scheduled work, not a production bandwidth measurement.

The internal `accountingOutbox:recoverPeriodHeldSupplierVat` migration pages the parked range 100 rows at a time. Its deployment-wide `supplierVatHoldMigration` singleton stores the cursor and completion marker in the same transaction as releases and scheduled claims. `rollout migration resumes beyond the first page of valid period holds` puts 101 valid holds before the invalid row, calls one page, then resumes from the stored cursor and requires one refusal attempt with no financial change. Owned-VAT and zero-VAT holds remain byte-identical. A repeated call after completion returns READY with zero reclassifications and changes neither the checkpoint nor scheduler records.

`scripts/rolloutRelease.mjs` invokes this page function after verifying deployment identity and before the empty-deployment success path, through the existing operator-key CLI wrapper. `scripts/releaseGuard.ts` runs pages serially to READY, shares the bank/Inbox rollout deadline and imposes a page cap; failed calls and malformed evidence refuse the rollout. Later deployments make only the completed-state probe. READY certifies reclassification, not completed quarantine or repaired settlement. This follows the bank rebuild's persisted-cursor MORE/READY rollout pattern (`bankBalanceBackfill:runPage`, `rebuildBankBalances`) and [Convex's migration guidance](https://stack.convex.dev/migrating-data-with-mutations). The posting-time VAT refusal precedes the only period-hold writer, so new invalid consigned VAT rows cannot enter this closed migration population. No new migration framework or recurring recovery is used.

The literal test `historical taxed settlement exact replay through direct returns the posted occurrence` calls `postAccountingEvent` directly. It first posts the taxed journal through that engine with owned evidence, restores consigned evidence, removes the period and replays the identical command. It must return the existing event and journal with `alreadyPosted: true`, changing no financial record. The outbox counterpart completes its duplicate row against the existing event before period or VAT eligibility checks. Payload, source and key collisions still refuse; reserved receipt authority is proven before either idempotency lookup. Outbox replay-proof failures record the fixed code `SUPPLIER_REPLAY_REFUSED` before any financial write. Only this read-only proof is caught; financial posting exceptions still escape and roll back. This follows [AWS's idempotent API guidance](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/): acknowledge the same request and reject changed parameters. It acknowledges historical VAT without correcting it.

The disposition follows `accountingOutbox.ts`'s `custodyPostingRefusal` and `failOutboxRow`: record an expected refusal before financial writes and before temporary holds. [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions) documents atomic scheduling from mutations and internal-error retries; [Convex error handling](https://docs.convex.dev/functions/error-handling/) allows typed expected-failure outcomes. The shared posting-engine guard covers direct calls as well as queue processing. The pure posting rule is not the enforcement point.

These are serial convex-test checks. Real-backend execution, OCC, authenticated EN/AR screens, independent review and production data are not proven. Already-posted consigned VAT is unchanged and needs an operator census and, where present, an approved correction. No production census or correction ran in this change.

## SCRUM-869-DUE-AGING

Owner ruling SCRUM-869#c23883 (2026-10-29, OQ-1), recorded in Jira by the coordinator as the record of a chat ruling; it is not the owner's own text, and the digest in `regression/rulings.json` is the sha256 of the whole markdown body of that comment. A supplier obligation's due date is derived on the server and explained: the agreed date, else the ownership-model trigger read from recorded facts only, else "No due date", which is never invented and never overdue. Aging buckets are Current, 1-30, 31-60, 61-90 and 90+ days overdue, in calendar days of `Asia/Amman`. Disputed amounts are shown separately and stay in the gross outstanding.

Coordinator rulings of 2026-10-29 that fix the open points inside c23883 (the trigger table is `DUE_TRIGGERS` in `convex/utils/supplierDueDates.ts`, one entry per ownership model, so an owner answer changes one entry and its test):

- Owner ruling SCRUM-869#c23906 (2026-10-29, given in chat and recorded in Jira by the coordinator; the digest covers the whole comment) replaces the first two coordinator defaults. "Completed delivery" is handing the car to the customer: a commission receivable is due on the recorded vehicle handover and nothing else, `handoverStatus` HANDED_OVER with its `vehicleHandoverAt`. `applications.registerVehicleHandover` writes both for every deal, CASH included (`finalizeDeal` refuses without it), so a CASH deal is read the same way; a sale recorded without a deal application has no handover record. ## SCRUM-869-DUE-ALERTS

Owner ruling SCRUM-869#c23883 (2026-10-29, OQ-1), the coordinator's Jira record of a chat ruling, not the owner's own text; the digest in `regression/rulings.json` covers the whole markdown body of that comment. Supplier obligations (payables, margin receivables, cost recoveries) raise in-app alerts through the existing `notifications` table: 3 days before the due date, on the due date, at 7 days overdue, then weekly. Disputed obligations and obligations with no due date are never alerted. Recipients are resolved on the server: the Owner, members holding `manage:finance` (Finance Manager) and members holding `view:finance` (authorised accounting staff), never an offboarding member and never a role of another organisation.

Design facts the cells rely on:

- The alert row is inserted directly. `utils/notifications.dispatch` is not used because it also fans out to email, WhatsApp and push; this ruling is in-app only.
- Idempotency is one `commandIdempotency` record per obligation, step, occurrence and recipient (`supplier-due-alert`, key `<kind>:<id>:<step>:<occurrence>:<userId>`), written in the same transaction as that recipient's alert row. Per recipient, because the fan-out for one obligation can span several transactions (PR #716 round 2).
- The cron `supplier-due-alerts` (05:30 UTC, 08:30 Amman) pages organisations, 20 per page, and schedules one worker mutation per organisation. A worker transaction reads one page (50 rows) of one obligation kind and at most `floor(400 / alerts)` memberships, sends at most 400 alerts (at most three documents written each: the notification, and the idempotency record's insert and patch, so 1,200 at the budget against Convex's 16,000 limit), and schedules its own continuation: the same obligation page with the next membership cursor, then the next obligation page, then the next kind. The budget of 400 is chosen from the documented limits, not measured: `convex-test` has no write meter. The worker does not catch its own failure: a fault that can be seen from a read (an unsupported currency, unconvertible amounts) is skipped with a log line and counted in `skipped` before any write, and any other fault throws, so the mutation rolls back whole and its continuation is dropped with it (a caught error would commit the writes before it and drop the rest of the organisation). Recipients are the active, non-disabled, non-impersonation members of the organisation's memberships, read one bounded membership page at a time rather than the first 1,000.
- Catch-up (coordinator ruling 2026-10-29, closing the missed-day gap): each run finds the latest schedule step whose Amman day has been reached (-3, 0, 7, then 14, 21, ... counted as occurrences) and sends it only when that step's idempotency record does not exist. A day the cron or an organisation worker missed is made up on the next run, once; earlier skipped steps are never sent as a burst, and a row that gains a due date late gets the one step it has reached.

- Stored dates are validated where the worker reads them (PR #716 round 3). A stored date that is not finite, or lies outside the JavaScript Date range of +-8.64e15 ms (ECMAScript TimeClip), cannot be formatted: `Intl.DateTimeFormat` throws a `RangeError`, which is not a `ConvexError`, so it used to escape the unreadable-row skip and starve the organisation. `renderableDate` in `convex/utils/supplierObligationDue.ts` now checks `vehicleHandoverAt`, `disbursedAt` (only when funding is counted as received), `paymentDueDate` and both `agreedDueDate` fields as the facts are built, and throws the named data fault, which the worker's existing unreadable-row path skips, logs and counts. It is not a catch-all: any other error still propagates.
- A worker failure leaves a durable signal (PR #716 round 3). A mutation that throws rolls back every write, including any record of its own failure, and drops its continuation, so the failure cannot be recorded from inside it. The scheduler and the cron run `runOrgSupplierDueAlerts`, an internal action that calls the worker, and on an error records the failure from a separate transaction (`recordSupplierDueAlertFailure`) and rethrows, so the scheduled function still fails visibly and is not retried. The record is one `cronHeartbeats` row (existing table and `by_job_ranAt` index, no schema change) under the per-organisation job name `supplier-due-alerts:<orgId>`, `success: false`, with a `detail` of at most 1,000 characters naming the organisation, kind, obligation cursor, recipient cursor and the error message. Repeated failures update that row in place while no intervening worker transaction succeeds. A later transaction that succeeds inserts one success row only when the newest heartbeat is a failure, which supersedes it; a clean run writes nothing. If each day's retry commits an earlier page and then fails on a later page, it adds two rows that day: one success and one new failure. `supplierDueAlerts.listSupplierDueAlertFailures` (super admin only, paginated) lists the organisations whose newest heartbeat is a failure. The per-organisation names are deliberately outside the fixed `CRON_HEARTBEAT_JOBS` list that drives the cron-status screen.

Evidence boundary: `convex-test` only. It has no runtime read limits, no OCC and no real scheduler clock, so bounded reads and the live cron are not proven here. The page-size constant (50) is not observable in these tests, because a larger page would still alert every row.
