# Agent skills

Shared skills for every agent session in this repository. Claude Code loads `.claude/skills/*/SKILL.md` automatically. They are guidance for how to work. They never replace `AGENTS.md`, the project instructions, Jira, or the repository's own gates.

> **Threat model for the enforcement below.** The session hook is a guardrail that stops an agent from forgetting skills on ordinary git commands. It is not a sandbox against a deliberately evasive process, which no Bash-text parser can be. Authoritative enforcement is the server-side `skill-evidence` check (form only) and the two seats' signed PR comments. Documented residual: programs or scripts that run git themselves, and deliberate evasion beyond the fail-closed classes.

## Precedence

1. `AGENTS.md`, the project instructions and the owner rulings (including SCRUM-760 and SCRUM-813).
2. `convex/_generated/ai/guidelines.md` for Convex code.
3. These skills.

A skill never lowers a gate. In particular:

- Money-touching changes still need the two-seat review (defined in the project instructions; if you do not have them, ask before merging any money change) on the final head SHA, or carried forward to it under the re-certification rule below (Seat 1: Opus 5.5 plus `/simplify` in a session separate from the implementer; Seat 2: Codex sol6 at medium effort or lower). Any subagent or "second opinion" a skill suggests is advisory and is not a seat.
- Never write `review-evidence/*.json`. Never claim a human review.
- The Production deploy approval in GitHub stays a human action.
- **Re-certification after the head moves (owner rule, 2026-10-19, set in the project chat).** A seat certifies one head SHA.
  - The PR's own code changed, or updating from main hit a merge conflict: both seats fully re-certify the new head.
  - The only change is a clean update from main and the PR's own diff is identical, including whitespace: carry the certification forward only with the complete API proof described under Enforcement. Re-run CI on the new head and note the original and carried SHAs on the PR and the Jira issue.
  - That clean update brought in main changes to code the PR touches or depends on: run one short, scoped re-review of only the interaction, recorded against the new head SHA before merging. On a money PR, both seats do it, Seat 1 in a session separate from the implementer. On other PRs, one independent read-only reviewer does it.
  - A re-check that was not run is recorded as not run. Never claim a seat for a head it did not read.
- Skills that ask a person a question are answered by the decision rule in the project instructions (consult Codex sol6, medium effort at most). Codex quota is low, so skills do not trigger extra Codex runs.

## Which skill when

| Situation | Skill |
| --- | --- |
| Diagnosing a bug, shaping a non-trivial change, reviewing your own diff, or about to say "done" | `engineering-principles` |
| Something is broken, failing, throwing or slow and the cause is not obvious | `diagnosing-bugs`. Build a red-capable feedback loop before forming any theory. Redact: this repository is public. |
| Fixing a bug | `tdd`. Mandatory for money and permission bugs: the test fails before the fix and passes after (SCRUM-761). |
| Any change to money, permissions, tenancy, schema, indexes, crons, webhooks or shared helpers, and every review of one | `blast-radius`. Prove the one fact the change is safe because of by running real code. |
| Reporting or acting on any performance, I/O or cost number | `benchmark-checklist`. Tie the number to its measured source and name the limiter. |
| Writing or editing TypeScript or TSX | `typescript-best-practices`. `convex/_generated/ai/guidelines.md` wins inside `convex/`. |
| Before asking for review seats on your own change | `two-axis-review`: advisory Standards and Spec check against AGENTS.md and the Jira issue. It is never a seat and is never labelled as an independent review. |
| PR bodies, commit messages, docs, runbooks, RFCs | `technical-writing`, then `unslop` on the text. The PR template and attribution block still apply. |
| Replies, Jira comments, review notes | `unslop` |
| The same agent mistake has shown up twice in this repo, including across sessions | `correct`. Invoke automatically on the second occurrence without waiting for a user request. Record evidence for both occurrences. Raise a normal PR; it needs its own review. |

## Enforcement (owner request, 2026-10-20)

The table above is no longer left to memory. Two mechanisms check it. Both read their path list and skill list from `scripts/skillEnforcement/policy.mjs`, so they cannot drift.

1. **Session hook** (`.claude/settings.json`, `scripts/skillEnforcement/skillGate.mjs`). Before `git commit`, `git push`, `gh pr create` and the GitHub MCP write tools, the hook reads the session transcript and denies the step unless the required skills were invoked with the Skill tool in this session.
   - Commit and push: `typescript-best-practices` is not gated: it loads itself when a `.ts`/`.tsx` file is read or edited (its `paths` setting), so a gate on it would deadlock sessions that never opened such a file. On any file under `convex/` (default deny: money, permission, tenancy, schema, cron and webhook code all live there; only `convex/_generated/` and non-source files are exempt) also `tdd` and `blast-radius`. On gate or production-safeguard files (`AGENTS.md`, `.github/`, `.claude/`, release scripts) also `blast-radius`.
   - PR creation: `technical-writing` and `unslop`. On money or gate paths also `two-axis-review` and `engineering-principles`.
   - If the changed files cannot be determined, the hook treats the change as a money change. A crash blocks the step (`onFailure: block`).
   - It counts a skill only when the `Skill` tool call returned without error, or when the user typed the `/skill` command. Assistant text that mentions a skill counts for nothing.
   - It scans the raw command for git, so `do`, `then`, `else`, `timeout`, `nice`, `!`, `sudo -u`, `bash -c 'git commit'`, `env git push` and `$(git commit)` are all caught. It skips git only as an argument to `echo`, `printf` or `grep`, so `echo git commit` is not a commit.
   - `git -C <dir>` and an earlier `cd <dir>` inspect that directory's files. `--git-dir`, `--work-tree`, `GIT_DIR=` and a dynamic `cd` make the files unknown, which is treated as a money change.
   - For `git commit` the hook adds the command's pathspecs (`git commit -m x convex/sales.ts`, `--only`, `-- <path>`; git expands directories and globs) and `-a`/`--all` to the staged files. It fails closed (treats the change as money) when it cannot read the arguments: `-p`, a `$(…)` or `~` argument, an unclosed quote, a path outside the repository.
   - Text piped into a shell (`… | bash`, `curl … | sh`, `| xargs sh`), `eval`, PowerShell `iex`/`Invoke-Expression`/`& $cmd`/`-Command`, a `sh -c` with a dynamic argument, a command word held in a variable (`$g push`) and git aliases (`git -c alias.*`, `--config-env`, or any subcommand that is not a git built-in) are gated as an unknown commit and push, whatever produces the text. Quoted text is skipped only on an allowlist of text-only commands (`echo`, `printf`, `grep`, `egrep`, `fgrep`, `rg`, `jira`, `gh pr`/`gh issue`, and the message of `git commit`), and only when the unquoted part of that segment has no shell word, `-c`/`-e`/`-Command`/`-ArgumentList` flag or runner (`pnpm`, `npx`, `find`, `watch`, `parallel`, `node`, `python`, `Start-Process`, …) and the quote does not execute (`"$(…)"`). Flags, runner words, the git command word and its subcommand are read after quotes and escaping backslashes are removed (`"git" push`, `'git' push`, `g"it" push`, `git "push"`, `"/usr/bin/git" push`, `git.exe push` are steps; one found only after normalising is an unknown step, so it counts as money) (`rg "--pre" sh`, `"sh" -c`, `git "-c" alias.p=push p` are the same commands as unquoted). A leading `VAR=value` (`EDITOR=`, `GH_EDITOR=`, `RIPGREP_CONFIG_PATH=`, …), a process substitution (`<(…)`) and the flags `--pre`, `--pre-glob`, `--hostname-bin` and `--editor` also turn blanking off, and `rg --pre`/`--hostname-bin` is gated as an unknown commit and push on its own because ripgrep runs the program it is given. So `grep -rn "eval(" src` and `jira comment add "git push failed"` never trigger, while `pnpm exec sh -c 'git push'`, `find -exec sh -c '…'`, `watch 'git push'`, `node -e` and `python -c` running git are all scanned and gated. An inline interpreter (`node -e`/`--eval`, `python -c`, `deno eval`, `bun -e`, `perl -e`, `ruby -e`) whose code mentions `child_process`, `execSync`, `execFile`, `spawn`, `subprocess`, `os.system`, `os.popen` or `Deno.Command` is gated as an unknown commit and push (for `perl -e` and `ruby -e` also `system`, `exec`, `qx`, backticks, `%x`, a piped `open`, `IO.popen`, `Open3` and `spawn`); a plain `node -e "console.log(1)"` is not. Code that reaches git some other way is a residual gap. A pipe into a shell stays gated even for harmless input (`curl … | sh`): its content cannot be known, so it is an accepted false block.
   - Class rule: after backslash-newline continuations are joined, a command word, or a git subcommand word, that the shell would expand, unescape or glob (`$'\x67it' push`, `${V:-git} push`, `git${IFS}push`, `{git,} push`, `./g*t push`, `$EDITOR`, `$(echo git) push`) is gated as an unknown commit and push, as is `git`/`git.exe` in any letter case (`GIT push`, `git.EXE push`). `xargs`/`parallel`/`find -exec` with `git` or a `git-*` helper as any later word (`xargs -I X git X`, `xargs -a list git`; `xargs echo git` is an accepted false block), git's dashed helpers (`git-push`, `/usr/lib/git-core/git-commit`, `git-push.exe`, any `git-<sub>` that is not a built-in other than commit/push) and any `alias` or `shopt … expand_aliases` in the command are gated the same way. On the git side any path, extension and letter case is ignored (`git.cmd push`, `xargs.exe -a f git.exe`); the quote-skipping allowlist matches only the bare command name, optionally `.exe`, so `./grep`, `echo.sh` and `jira.cmd` keep their quotes scanned. Plain words (`git log`, `./scripts/x.sh`, `pnpm test`, `rg`, `grep`) are not affected; `$EDITOR file` and `$HOME/bin/tool` are accepted false blocks.
   - Known false blocks (fail closed, accepted): a commit that touches only `convex/` test files still needs `tdd` and `blast-radius`; a quoted example or heredoc body with `git push` after a separator; `ls git push`. Residual gap: a script or program that runs git itself.
   - It proves a skill was invoked, not that it was followed. An agent can still edit the hook, so it is a guard on mistakes, not a boundary.
2. **`skill-evidence` PR check** (`.github/workflows/skill-evidence.yml`). A PR that touches a money, permission or gate path must carry a `## Skill evidence` section in its body: skills run, red-run and `/simplify` output, both seats' models and certified SHAs, Seat 2 effort, and either a Seat 1 session link or the local fields below. The check fails when the section is missing, still a placeholder, shows a red run with no failure sign (a non-zero failed count, `FAIL`, `AssertionError`), names the implementing session (in the body or a PR commit trailer) as Seat 1, gives a model or effort that is not exactly Opus 5.5 (Seat 1) or `gpt-6-sol` / `gpt-6.1-sol` at low or medium (Seat 2), or cites a SHA that is not in the PR. Sol 6.1 needs a Codex CLI that serves it: 0.156.1 rejects `gpt-6.1-sol` ("not supported when using Codex with a ChatGPT account"); codex-cli 0.164.0-alpha.11.1 (the desktop app's bundled binary) runs it. It runs from `main` (`pull_request_target`), so a PR cannot loosen its own check, and it never reads or writes `review-evidence/*.json`.
   - A change that touches only test files and docs may replace the red run with `Red run: No behaviour change: <reason>`. It is valid only when no changed file is money or permission source (a `convex/` file that is not a `*.test.*`/`*.spec.*` file) and both the Seat 1 SHA and Seat 2 SHA lines also say "no behaviour change". Any sensitive source file needs a real red run.
   - The red run fence must name a test file that is in the PR diff and show a failure (a non-zero failed count, `FAIL`, `AssertionError`). The `/simplify` output must be at least 40 characters and name what was reviewed (reuse, simplification, efficiency, altitude, or no changes/findings).
   - **The check verifies form and local-report consistency.** It cannot prove a review happened or that the output is real. The seats' own signed PR comments are the authoritative evidence, and the check says so in its output.
   - URL-based evidence stays compatible. For a local Claude review, use `Seat 1 session: local:<UUID>`, `Implementer session: <UUID>`, and `Seat 1 review: https://github.com/<owner>/<repo>/pull/<number>#issuecomment-<id>`. The reviewer must be a different session. The certified SHA must be the full current head unless the certificate carries under the conditions below. The check fetches that same-PR comment through the fixed GitHub API endpoint and requires an owner, member or collaborator to have published it. A coordinator may transport the review verbatim, with that transport disclosed.
   - The local reviewer supplies these exact lines in its signed report: `Local Claude session: <UUID>`, `Local Claude model: claude-opus-5-5`, `Local Claude effort: high`, `Local Claude SHA: <full reviewed SHA>`, `Local Claude verdict: CERTIFY`, and `Signed: <reviewer>` (at least five characters). Missing, duplicate or inconsistent report fields refuse. Reports containing HTML comments refuse, so hidden fields cannot contradict the rendered report. An unreadable comment is unavailable, never a pass. The implementer checks the local transcript and runtime model/effort before publishing; the server checks report consistency, not the authenticity of model execution or a cryptographic signature. Never label this as human review.
   - Seat evidence must be in the PR body. Cloud Seat 1 and Seat 2 certified SHAs may be the head or a commit in the PR's own range, not an older commit on `main`. Only local Seat 1 has the exact-head requirement and the carry exception. Seat 2's model, effort and SHA rules are unchanged.
   - **Local certificate carry, SCRUM-874.** A signed report at commit C carries to head H only when C is a full SHA in this PR's complete commit list and the report passes every existing session, model, effort, signature and CERTIFY rule. Walking H's first-parent path back to C must find only merge commits in this PR. Every non-first parent must be reachable from the sampled `main` SHA. An ordinary commit, an unrelated merge parent or a broken ancestry proof requires a new exact-head certificate.
   - At the same sampled main SHA, the check compares `main...C` with `main...U` for **every** update commit U on the first-parent path through H. Each comparison must have the same file names, rename paths, statuses, before/after modes and contributed lines in order. Hunk positions are ignored by the patch parser; whitespace and end-of-file newline markers are preserved. Independently, Git trees must show identical reviewed blob SHAs and types at C and U, and identical base blob SHAs and types at the old and new merge bases, using the old path for renames. Matching absence is required for added and removed files. Complete tree diffs must agree with the API's changed-path sets. A relocated edit or an intermediate change restored by H therefore refuses carry. Missing, binary, malformed or truncated patches refuse carry. So do incomplete commit lists, saturated compare file lists, truncated trees, API errors, rate limits and unexpected response shapes.
   - At every update, no file touched on main between the old and new merge bases may appear among the PR's changed paths, including old rename paths. The check reads each intervening main commit, so a touch followed by a revert also refuses. Missing pagination evidence refuses carry. Together with complete changed-path sets and blob identity at each update, this proves the API-only, file-disjoint merge case. Ancestry alone does not prove merge purity. This disjointness proof does not prove safety for dependencies in other files; the scoped interaction review rule above still applies.
   - Successful output says the certificate was carried from C to H and lists the update commits, file count, merge bases and disjointness proof. It does not claim that a seat certified H. Required CI must still pass at H under the existing checks; `skill-evidence` does not judge those checks. A failed carry condition names the reason and requires exact-head evidence. Editing or deleting the original signed report still rechecks and revokes the carried result.
   - [Gerrit's copyCondition documentation](https://gerrit-review.googlesource.com/Documentation/config-labels.html#label_copyCondition) supports sticky Code-Review votes for `changekind:TRIVIAL_REBASE`, which requires the same diff including context lines and no conflict resolution. This checker uses blob identity with merge ancestry and file disjointness; it does not claim a general ordering of strictness against Gerrit. [Git merge-tree](https://git-scm.com/docs/git-merge-tree) computes the native merge result without touching the index or worktree. This API-only checker instead proves the restricted disjoint case at every update and refuses when that proof is unavailable. [Graphite's action](https://github.com/withgraphite/dismiss-stale-approvals) preserves approvals when `git range-diff` is unchanged. [GitHub's native stale-review setting](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging) dismisses approvals when the merge base introduces new changes. The implementation uses [compare pagination and its 300-file limit](https://docs.github.com/en/rest/commits/commits#compare-two-commits), the [250-commit PR limit](https://docs.github.com/en/rest/pulls/pulls#list-commits-on-a-pull-request), and [Git tree object SHAs, modes and truncation flags](https://docs.github.com/en/rest/git/trees#get-a-tree). Saturated lists refuse rather than infer completeness.
   - Editing or deleting a referenced local report invokes `skill-evidence-refresh.yml` from the default branch. Its separate job publishes the actual recheck result as `skill-evidence` on the PR head, rather than the default-branch event SHA. Only this refresh job has `checks: write`; the ordinary judge retains read-only permissions. Unrelated comments produce no replacement result and cannot cancel a pending revocation check: cancellation groups include the comment ID. Successive changes to that same report cancel obsolete runs. A revoked or unreadable report produces failure. The operator still reads all review surfaces and revalidates evidence immediately before merging.
   - The checker returns the head it measured; the refresh refuses to approve a different head. If the Checks API cannot publish, the refresh is unavailable evidence even if an older result remains green. That blocks merging until a successful live recheck. Creation events are unnecessary for revocation: a previously verified comment already exists, and deleting it cannot recreate its ID.
   - The check validates form and consistency. It cannot prove the text is true. Session links or the local signed PR report let the owner inspect the evidence. API access follows [GitHub issue-comment documentation](https://docs.github.com/en/rest/issues/comments#get-an-issue-comment). Both workflows retain base-branch execution and minimum job permissions, following [GitHub Actions secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use); neither checks out or executes PR code.
   - It is only a gate once it is a required status check on `main` (repository setting). Until then a red result is visible but does not block merge.

The section template is `TEMPLATE` in `scripts/skillEnforcement/prSkillEvidence.mjs`; the check prints it on failure. Neither mechanism is a review seat, and neither replaces the two-seat review.

The pilot bug hunters (SCRUM-760) are not skills. Scenarios they find become backend tests or browser replays through `tdd` and SCRUM-761.

## Not adopted

From pstack (56 skills): These were read and left out on purpose:

- `poteto-mode` and its 23 playbooks, `figure-it-out`, the `orchestrate`, `autopilot-*`, `shipping` and `babysit` playbooks: tied to Cursor's subagent and model setup (Grok, `pstack-models.mdc`), and their autonomy rules (arm merges, land stacks, "never block on the human") conflict with the two-seat review, the deploy gate and the decision rule here.
- `architect`, `arena`, `swarm`, `interrogate`, `how`, `why`, `teach`, `recall`, `reflect`, `no-comments` with the `comment-sicko` agent: need Cursor's Task tool and model slugs, and Slack, Datadog and Linear sources we do not use. `interrogate` is a multi-model review panel, which would duplicate or blur the two-seat review. The comment-deletion rules are not this repository's convention.
- `setup-pstack` writes to `~/.claude/rules`, and `automate-me` edits personal skills. Both change the user's environment.
- `make-bot-ui` pipes a downloaded installer into `sudo sh` and joins the machine to a Tailscale network. Rejected on security grounds.
- `show-me-your-work`, `create-verification-skill`, the formal-verification skills, `sharpen`, `ketchup`, `bro`, `in-your-own-words`, `poteto-help`: overlap Jira, the status checklist and the existing Playwright scenario work, or add context cost for little gain.
- The `principle-*` skills are folded into `engineering-principles`, minus `outcome-oriented-execution` (allows planned intermediate breakage), `never-block-on-the-human`, and the Cursor-specific `guard-the-context-window`.

From Matt Pocock's skills (27 listed at aihero.dev/skills, MIT, `mattpocock/skills`):

- `grilling`, `grill-me`, `grill-with-docs`, `to-questionnaire`: interview the user and wait for answers. Threads here work without approval waits and use the decision rule instead.
- `to-spec`, `to-tickets`, `implement`, `implement-spec`, `triage`, `setup-matt-pocock-skills`: built around GitHub or GitLab issues and parallel worktree fleets that merge themselves. `wizard` generates a script that writes `.env` values and GitHub secrets, so it is rejected on security grounds. The tracker here is Jira, and merges follow the repository gates.
- `pr`: its PR body template conflicts with the required attribution block and Before/After/How format. Its one-way or two-way door and blast radius idea is already covered by `blast-radius`.
- `domain-modeling`, `codebase-design`, `improve-codebase-architecture`: would create a glossary and decision records, or propose refactors, in a money codebase without an owner ruling. Revisit if the owner wants a glossary.
- `wayfinder`, `prototype`, `research`, `retro`, `handoff`, `teach`, `wait-what`, `ask-matt`, `writing-for-agents`: overlap `correct`, the existing handoff flow, or what Claude does by default.
- The `misc` and `in-progress` skills, including `git-guardrails-claude-code`, which blocks `git push` and would stop threads from delivering work.
- Its `diagnosing-bugs` and `code-review` are adopted in adapted form. `code-review` is renamed `two-axis-review` so it does not shadow the built-in `/code-review`. Its `tdd` rules are folded into the existing `tdd` skill.
